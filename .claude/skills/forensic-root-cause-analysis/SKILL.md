# Root-cause forensic investigation, before the fix

Every real incident in this project's history — `join_game` wiping the authenticated session on a character switch, the `saveQueues` capture race, `dg_cloud_email` in `localStorage` being read as if it were "currently logged in," a character name applying after the save it should have been in — had the same shape: two pieces of state that were each individually reasonable and disagreed under timing, ordering, or persistence. None of them were a typo. All of them survived at least one earlier "fix" of a sibling bug before being found again. This skill exists because "I found *a* cause and the repro stopped failing" has not been a reliable stopping point on this project.

## Why stopping at the first plausible cause fails here
Google's SRE postmortem practice draws a hard line between the **trigger** — the specific action that activated the bug — and the **root cause** — the structural condition that made the trigger dangerous in the first place ([Google SRE Workbook, Postmortem Culture](https://sre.google/workbook/postmortem-culture/)). In one of their published examples: *"A longstanding input validation bug ... was triggered by the manual reexecution of a workflow."* The fix was not "train people not to re-run workflows" — it was closing the structural gap the trigger merely exposed. Applied here: for `join_game`, the *trigger* was the Ghostdex re-emitting `join_game` on every character switch; the *root cause* was the handler unconditionally rebuilding `players[socket.id]` from scratch instead of merging into what was already there. Fixing only "don't re-emit on character switch" would have left the unconditional-overwrite handler live for the next feature that happens to reconnect mid-session — the actual fix (`server/index.js`, `join_game` handler, comment dated 22/08/2026) preserves `existing` and merges. Always write down both trigger and root cause separately; a report with only one is incomplete.

## The causal-chain map (do this before reading the "fix")
For the state involved in the bug, write down, in order: which client event fires → which in-memory JS variable it reads → which `localStorage` key it reads *that might be stale relative to that variable* → which socket event it emits and in what order relative to any other emit in flight → what the server handler does with the *authenticated* identity vs. the payload's claimed identity → what the SQL statement actually does (UPSERT? full-column overwrite? JSONB merge or replace?) → whether anything reads this data back before the write is confirmed committed. Do this as a literal list before forming a hypothesis — the gap is almost always between two adjacent links in this chain, not inside either one alone.

## Ordering/race bugs: find the raw divergence before theorizing
This project's clearest documented example is `saveQueues` (`server/index.js`, comment dated 22/08/2026): `save_game_state` fired multiple independent `pool.query()` calls per socket with no ordering guarantee on *completion*, only on receipt — so an older snapshot's query could finish after a newer one's and silently overwrite it. A field debugging account of exactly this class of bug ([Kartik Khare, "Me vs a Race Condition at 2 AM"](https://kharekartik.dev/writing/debugging-race-conditions-in-distributed-systems/)) distills the method: query the **raw persisted state directly** (bypass the app layer — `SELECT` the row yourself, don't trust the client's "saved!" toast), narrow to the specific record and time window, reconstruct broken-vs-healthy timelines side by side, and locate the exact point the sequences diverge. Its central insight applies directly to reviewing any lock/queue fix here: *does the guard enforce ordering at the exact unit where correctness is required?* `saveQueues` is keyed per `socket.id` — correct, because ordering only needs to hold within one player's own sequence of saves, not across players. When reviewing a proposed serialization fix, check the key it's scoped by against what actually needs the guarantee — a queue keyed too broadly (e.g., globally) stalls unrelated players; one keyed too narrowly (e.g., per-event-type instead of per-connection) doesn't actually close the race.

## Stale-cache/session bugs: identify which value is the source of truth *right now*
The `dg_cloud_email` incident (`js/web2/game_core.js`, comments dated 22/08/2026) is this project's clearest case of a **read-your-writes** violation: `localStorage.getItem("dg_cloud_email")` persists across reloads and was being read as proof of an active session, when the actual live-session marker was the in-memory `g_hasAuthenticatedThisPageLoad`, reset every page load. A persisted cache and a live-session flag will agree during normal use and silently diverge exactly when it matters (closed tab, reopened without re-login) — the standard framing is that a session must read from something that tracks "did *this* session actually authenticate," not something that merely tracks "did authentication ever happen on this device" ([session/read-your-writes consistency, GeeksforGeeks](https://www.geeksforgeeks.org/system-design/read-your-writes-consistency-in-system-design/); [Redis Engineering, "Cache Consistency: Strategies to Keep Data Fresh"](https://redis.io/blog/cache-consistency-strategies/)). When investigating any "acts logged in but shouldn't be" or "acts logged out but shouldn't be" bug, explicitly ask: which of the two values involved is scoped to *this session* and which merely *outlives* it? A fix that swaps which one gates a security-relevant check is a root-cause fix; a fix that just special-cases the one broken caller is a patch.

## Five Whys, written down — not just the last answer
Ask "why" repeatedly past the first plausible answer, but write down the whole chain in the report, not just the terminus — the third or fourth "why" is usually where a one-off patch turns into a structural one ([Five Whys technique overview](https://www.freecodecamp.org/news/from-symptoms-to-root-cause-how-to-use-the-5-whys-technique/)). Keep each "why" aimed at the process or the code path, never at a person — this project's incidents are the product of a fast-moving solo/small-team workflow shipping features quickly, not carelessness, and a "why" chain that lands on blame has stopped being diagnostic.

## Hunt for siblings before closing the investigation
Once you can name the bug's *shape* (not its instance), grep both `danger ghost/js/` and `danger_ghost_mobile/www/js/` for every other place that shape could recur: every other socket handler that overwrites an object instead of merging, every other check that reads a persisted `localStorage` key where it should read a live in-memory session flag, every other multi-emit sequence with no per-connection serialization, every other JSONB column written as full-replace instead of merge. This project has already had the *same shape* of bug recur in a new location after the first instance was declared fixed at least twice — treat one repro as proof the shape exists, not proof you found every instance of it.

## Reporting format
Structure every finding as: **trigger** (what specific action set it off) → **root cause** (the structural gap the trigger exposed) → **mechanism** (the exact causal chain, states named, not "the save race" as a label) → **fix classification** — borrow Google SRE's categories (Prevent / Mitigate / Detect / Repair) so the project owner can see at a glance whether something closes the gap for good, reduces blast radius, adds a tripwire, or just repairs the one instance found → **verified how** (the specific real-database test that proves it, per `e2e-db-verification`) → **known-open risk** (what you found but didn't fix, and why, stated honestly rather than implied-fixed).

## Red flags that mean the investigation stopped too early
- You can describe *what* broke but not *why* the same shape wasn't caught by the fix applied to its last sibling — that gap is often where the real structural cause is hiding.
- The fix only works when tested in the exact sequence/timing the bug was originally reported in — you haven't actually tested the ordering, you've tested one instance of it.
- The fix touches only the code path where the symptom surfaced, and you haven't grepped the other client (web vs. mobile) or other handlers for the same shape.
- Your explanation names a single line of code as "the bug" for something that only manifests when two independently-reasonable pieces of state disagree — that's usually a sign you found *a* trigger, not the root cause.
