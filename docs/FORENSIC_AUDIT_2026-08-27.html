§1 Críticos

Perda de progresso real ou manipulação trivial de dado persistente. Nenhum é teórico — todos têm gatilho concreto identificado no código hoje em produção.

Salvar personagem sobrescreve em vez de preservar — sem COALESCE

crítico
server/db.js — saveCharacters() js/game/ghost_inventory.js
Gatilho real, não hipotético

UnlockGhostForPlayer() monta um objeto de personagem com só 11 dos 21 campos da tabela toda vez que o jogador "captura" um fantasma que o cache local do aparelho não conhece — inclusive um fantasma que já existe no banco, capturado antes por outro aparelho da mesma conta. Dois exemplos convergentes: o mesmo Fantasma #005, evoluído no celular, reaparece pro jogador no PC (cujo cache local ainda não sabe do #005) — capturar de novo lá manda um personagem "recém-nascido".

Causa raiz

characterToRowValues() preenche todo campo ausente com um default fixo em JS, e o UPSERT faz SET col = EXCLUDED.col pra todas as 21 colunas sem exceção — inclusive as que o payload nunca tocou. savePlayerProgress (tabela players) já usa COALESCE($n, coluna) exatamente pra evitar isso; o conserto nunca foi espelhado pra characters.

Consequência concreta

O personagem evoluído do celular — nível, inventário, equipamento, tudo — é apagado e substituído pela versão nível 1 vinda do PC. Perda de progresso permanente, silenciosa, sem nenhum aviso ao jogador.

Correção proposta

Trocar pra COALESCE(EXCLUDED.col, characters.col) coluna a coluna. Cuidado: isso muda o comportamento de "primeira captura" (que hoje depende do default JS preencher os campos ausentes) — a correção certa provavelmente precisa diferenciar INSERT (preenche default) de UPDATE (preserva existente), não só trocar a cláusula.

Verificação: não testado contra o Postgres real nesta rodada — recomendado antes de fechar: criar personagem com inventário/equipamento reais, mandar um save_game_state parcial pro mesmo characterId, confirmar se os campos sobrevivem.

Servidor confia cegamente em level/stats/itens vindos do cliente — "anti-cheat" existente é decorativo

crítico
server/index.js — save_game_state js/game/engine.js — SHADOW STATE rpg_system.js — rpgAntiCheat
Exploit real, reproduzido

Depois de um login normal, window.NetworkState.socket é global. Qualquer jogador abre o console (F12) e roda:

window.NetworkState.socket.emit('save_game_state', {
  characters: [{
    characterId: 'ghost_001',
    level: 999999999, vit: 9999, pow: 9999,
    weapon: { name: 'GodBlade', damage: 999999 }
  }]
});

O servidor grava exatamente isso, permanentemente, sincronizado em todo aparelho da conta.

Por que o "anti-cheat" não pega isso

O hash de integridade em engine.js (window.g_score) tem um setter público que recalcula o próprio hash pra bater com qualquer valor atribuído — o cofre se autodestranca pra combinar com o que você acabou de girar. O rpgAntiCheat de rpg_system.js tem a mesma falha estrutural: hash calculado no mesmo processo que deveria vigiar. Nenhum dos dois é corrigível no cliente — a proteção real só pode existir no servidor.

Correção proposta

Validação de faixa plausível no servidor pra level/xp/atributos/score antes de gravar; catálogo server-side de armas/itens válidos em vez de aceitar objeto arbitrário; impor o limite de 5 fantasmas por conta no servidor, não só na UI.

Confiança: alta — exploit reproduzido e confirmado, não hipotético.

Equipamento inteiro é apagado ao carregar um save legado — só no site

crítico
rpg_system.js — loadLocalStorage(), 2 ocorrências
Gatilho

Um personagem cujo save ainda tem uma chave legada helmet ou spell (formato anterior à migração pros slots atuais), mesmo convivendo com itens válidos nos slots novos.

Causa raiz

A condição do site dispara o reset completo com typeof state.equipment.helmet !== 'undefined' — presença de qualquer chave antiga já zera state.equipment inteiro. O mobile corrigiu isso: só apaga as duas chaves legadas, preserva o resto.

Correção proposta

Portar a lógica do mobile pro site nas duas ocorrências — delete state.equipment.helmet; delete state.equipment.spell; em vez de reatribuir o objeto inteiro.

Verificação: não testado contra o banco real — recomendado antes de fechar: contar quantos personagens no Postgres ainda têm chave helmet/spell residual, pra medir o dano já feito.

Entrar na fase secreta CAVE1 quebra o save do personagem inteiro, em silêncio

crítico
rpg_system.js — worldLevel sem normalizar server/db.js — characterToRowValues() schema: world_level INTEGER
Cadeia causal completa

CAVE1 é uma fase real e jogável — o jogo grava g_currentLevel = "cave1" (string). Desde a correção de hoje "salvar a fase também", todo save automático copia esse valor cru pra state.worldLevel, sem normalizar. A string "cave1" chega direto no parâmetro SQL de uma coluna INTEGER. O Postgres rejeita com erro de tipo — e como o save roda em BEGIN...COMMIT, isso derruba a transação inteira: não só world_level falha, o personagem inteiro (nível, XP, atributos, equipamento) para de salvar, silenciosamente, até o jogador sair da caverna.

Por que passa despercebido

Na sessão em memória do jogador tudo continua subindo normalmente — só diverge do banco. Um segundo aparelho logando durante ou logo após a visita à CAVE1 recupera o personagem congelado no estado de antes de entrar.

Correção proposta

Normalizar worldLevel com a mesma lógica que network.js já usa (normalizeLevelName()) antes de gravar em state.worldLevel; e/ou validar o valor em server/db.js antes do INSERT, com fallback seguro pra qualquer string não-numérica futura.

Confirmado nas duas plataformas. Verificação recomendada: entrar na CAVE1, disparar um autosave lá dentro, checar world_level no Postgres direto.

§2 Altos

Bugs reais e reproduzidos, sem risco de perda de dado tão direto quanto os críticos, mas afetando jogadores de verdade hoje.

Checkpoint de seleção de personagem no mobile usa sessão obsoleta — irmão exato de um bug já corrigido

alto
www/js/game/engine.js — handler de SPACE
O achado

Seis linhas abaixo, no mesmo handler, existe um comentário explicando por que dg_cloud_email (persiste entre reloads) não pode ser usado como prova de sessão — só g_hasAuthenticatedThisPageLoad (reseta a cada carregamento) é confiável. Um checkpoint adicionado depois, no mesmo arquivo, reintroduz exatamente esse padrão: usa !!localStorage.getItem('dg_cloud_email') pra decidir se mostra a tela de seleção de personagem, e dispara antes do gate correto — pulando o modal de login mesmo sem autenticação real nesta carga de página.

Correção proposta

Trocar por window.g_hasAuthenticatedThisPageLoad, a mesma fonte de verdade do gate vizinho — ou mover o checkpoint pra depois dele.

Site não tem sistema de stats por espécie — mobile tem

alto
rpg_system.js — getGhostBaseStats() ausente no site
O achado

resetStats() no site sempre volta pra {vit:1, agi:1, int:1, pow:1, mag:1}, igual pra qualquer espécie — enquanto ghost_inventory.js (idêntico nas duas plataformas) já calcula stats iniciais por espécie na captura. O site discorda de si mesmo. O mobile resolveu isso com getGhostBaseStats(), ausente no site. Efeito colateral: usedPoints é calculado assumindo base sempre 1, então uma espécie com stat base alto recebe menos pontos pra distribuir do que deveria.

Correção proposta

Portar getGhostBaseStats() e os três pontos que a usam (getStats, resetStats, loadLocalStorage) do mobile pro site.

HP de boss dá um salto de até 20× da fase 9 pra 10

alto
js/game/engine.js — getPhaseMultiplier()
Confirmado ao vivo

Mesmo personagem (nível 50), mesmo boss (demon_fly): 1.000 HP na fase 5, 20.000 HP na fase 10 — 20× em 5 fases, contra um crescimento suave de 5× da fase 1 até a 5. O multiplicador muda de "= número da fase" pra "= número da fase × 10" exatamente na virada 9→10, sem transição — um degrau, não uma curva desenhada.

Correção proposta

Decidir a curva pretendida (ex.: progressão geométrica suave, como já usada pros fantasmas selvagens) e substituir o degrau por ela.

Jogando o site pelo celular, não dá pra usar nenhuma das 4 habilidades de combate

alto
index.html — #mobileControlsContainer

Os botões de toque pra V/F/E/R existem no código — só que apenas nas cópias mortas (www/index.html do site, e o app separado). O index.html real da raiz, que é o que o site ao vivo carrega, só tem mover/pular/pausar e o feitiço equipado (tecla 1). §3 Médios

Reais, mas de risco ou frequência menor — cada um isolado, baixo risco de regressão ao corrigir.

médio

Progresso da Ghostdex pode se perder entre duas abas da mesma conta

Cada aba grava ghostdex_progress/favorites como substituição total do JSONB, não merge — saveQueues só ordena saves dentro de uma conexão, não entre duas abas abertas ao mesmo tempo. Risco arquitetural coerente com o código, não confirmado ao vivo (a auditoria não pôde criar a segunda sessão de teste necessária).

médio

save_game_state/delete_character sem rate limit

O limite adicionado hoje cobre só login/cadastro/sessão. Uma conta autenticada pode emitir saves em loop apertado, cada um abrindo uma transação Postgres real.

médio

Ordem de prioridade errada em loadLocalStorage(), só no site

Checa window.cloudSave antes de saber se há um personagem específico pedido — se o global estiver setado por resíduo de outro fluxo, ignora a troca de personagem pedida pelo jogador. Mobile já inverteu essa ordem.

médio

PlayAsGhost() pode disparar reinício de jogo duas vezes, só no site

SelectCharacterToPlay() já inicia o jogo sozinho no site, e o final de PlayAsGhost() checa de novo e pode disparar uma segunda vez — mobile resolveu com uma trava de reentrância que o site não tem. Não confirmado em runtime.

médio

Auto-seleção do primeiro personagem ausente no mobile

Sem dg_deso_character_id local (comum em aparelho novo com personagens vindos da nuvem), o site escolhe o primeiro personagem sozinho; o mobile deixa o jogador na tela de seleção manual mesmo tendo personagens sincronizados.

médio

Direção do sprite espelhada ao contrário entre site e mobile

Pra jogadores com sprite custom equipado, a lógica de espelhamento (esquerda/direita) está sistematicamente invertida entre as duas plataformas — mesmo padrão em 2 pontos do código. Não determinado qual lado está certo sem confirmação visual.

médio

Guarda de posição malformada ausente no mobile

O site descarta com segurança um payload de posição de outro jogador com x/y não-numérico antes de desenhar; o mobile não tem essa guarda — risco de glitch/erro no WebView do Android, não confirmado em produção.

médio

3 scripts carregados duas vezes no mobile, com versão desatualizada na segunda cópia

ghost_inventory.js, ghostdex_data.js, ghostdex_ui.js aparecem no topo (versão nova) e de novo no fim do <body> (versão velha) do www/index.html. Sem efeito funcional confirmado hoje, mas evidência clara de processo de versionamento quebrado.

médio

Os dois APKs publicados hoje não são o mesmo build

danger ghost/DangerGhostMobile.apk (39.884.953 bytes, 27/08) e danger_ghost_mobile/DangerGhostMobile.apk (39.851.981 bytes, 23/08) divergem — o rebuild de hoje só foi copiado pro site, não de volta pro próprio repositório mobile. Falha de processo minha, de hoje mesmo — fácil de fechar rodando o build e copiando pros dois lugares juntos.

médio

Ghost Mode pode travar ligado se reatribuído a outro slot que não F

No slot padrão F, soltar a tecla desliga sem checar mana. Reatribuído a V/E/R, vira toggle e desligar também exige mana ≥ 10 — com mana entre 0 e 10, apertar pra desligar não faz nada até a mana zerar sozinha (menos de 1s, mas real).

médio

Trocar de fase reseta cooldown de habilidade — dá pra abusar de Phantom Form

nextLevel() e prevLevel() zeram skillCooldowns/phantomFormTimer incondicionalmente, inclusive pela porta de volta (sem matar boss nenhum). Andar até a porta e voltar repetidamente mantém Phantom Form disponível bem mais que o cooldown pretende.

médio

Cards de modal colam nas bordas da tela em mobile

Login, leaderboard, novo fantasma e perfil usam width:90% sem box-sizing:border-box — a margem de 5% pretendida vira 0px reais a 375px. Correção de uma propriedade CSS em 4 lugares.

médio

Duas linguagens tipográficas coexistindo

Login e HUD usam as fontes padrão do jogo (Orbitron/Inter) corretamente; seleção de personagem, novo fantasma, game over, leaderboard e perfil usam 'Courier New', monospace fixo, ignorando as variáveis CSS estabelecidas.

médio

Regressão do botão de pulo no app mobile continua presente

Já documentada em docs/UI_MOBILE_REVIEW.md (18/08) — reconferida hoje, segue idêntica: o botão com visual de "pulo" está de fato ligado à tecla F (Ghost Mode), e duas referências de toque apontam pra elementos que não existem no HTML. Nada foi corrigido nesse arquivo desde então.

§4 Baixos / informativos

Sem urgência — registrados pra não se perderem, não pedem ação imediata.

baixo

Vazamento inconsistente de mensagem de erro interna

3 handlers (auth_google_token, cloud_save_login, cloud_save_signup) repassam a mensagem crua de um erro inesperado (não os erros de propósito) direto pro cliente — os outros 3 handlers do mesmo arquivo já usam o padrão certo (mensagem genérica + log só no servidor). Correção mecânica.

baixo

kill_boss/player_attack sem autenticação, mas mortos hoje

Nenhum código do cliente emite ou escuta esses eventos — impacto prático zero. Se forem reativados um dia pra combate sincronizado, precisam da mesma checagem de sessão que save_game_state já usa.

baixo

Chat global permite forjar remetente "SYSTEM"

O broker MQTT é público; qualquer um pode publicar no tópico do chat com nick:"SYSTEM". Mensagens já são escapadas contra XSS — o risco é engenharia social/phishing, não execução de código.

baixo

Fase 1 não tem boss travando a porta

Só CAVE1 (área secreta) e as fases 4,5,6,10,11,16,17,18,20,21,22,33 têm boss fixo — a fase 1 numérica não está na lista. Provavelmente intencional (tutorial suave), vale só uma confirmação de design.

baixo

Código morto adormecido em PlayAsGhost() usando nível salvo por-dispositivo

Um segundo bloco redundante usaria dg_saved_level (compartilhado entre todos os personagens do aparelho, não por personagem) pra iniciar o jogo — hoje inatingível na prática, mas do mesmo formato de bug já visto neste projeto ("dado de personagem vazando pro nível de dispositivo"). Vale remover por higiene.

baixo

Fantasma selvagem em fase avançada pode dar XP suficiente pra pular dezenas de níveis

Observação de balanceamento, não bug de lógica — na fase 33, uma única captura pode valer ~637 mil de XP. Pode ser recompensa intencional por chegar tão longe.

baixo

Condição de correção retroativa de stats mais permissiva no mobile

Site só recalcula stats de nível 1 se vit > 20; mobile recalcula sempre que nível é 1, sem esse filtro. Parece inofensivo na prática (convergem pro mesmo valor), mas vale confirmar com quem desenha o RPG.

baixo

Texto "Lv." sem fonte definida no mobile (3 ocorrências)

O site define bold 9px Arial antes de desenhar o nível; o mobile herda a fonte do nome (mais fina), deixando o indicador de nível menos destacado no app. Cosmético.

baixo

Cor oficial de perigo (#FF0055) não existe em nenhum CSS do jogo

O CSS usa #FF0000 puro pra tudo que é perigo/fechar; #FF0055 só aparece dentro do canvas (borda de cooldown de magia). Deriva de paleta, não afeta o jogador.
